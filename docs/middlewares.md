# Middlewares (Express JS)

Express.js middlewares enable the execution of shared logic across all incoming HTTP requests or specific subsets of routes handled by the connector. They facilitate tasks such as request preprocessing, response handling, logging, and performance monitoring.

For additional information, refer to the official Express.js documentation: [Using middleware](https://expressjs.com/en/guide/using-middleware.html).

---

## New Relic / Trace-ID Middleware

**File:** `integration-events-common/src/common/newrelic-middleware.ts`

### Purpose

The trace-ID middleware provides end-to-end traceability across all hops in the event-processing chain. It extracts, generates, and propagates three identifiers on every request:

| Field | Meaning |
|-------|---------|
| `origin-unique-id` | Chain-wide identifier — stays the same across all hops |
| `caller-unique-id` | The previous hop's `called-unique-id` |
| `called-unique-id` | Always freshly generated by the current hop |

These are attached to `req.traceIds`, included as response headers, and appended to the request logger. New Relic custom attributes are gated behind `ENABLE_NEW_RELIC=true`; all other behaviour (log enrichment, response headers, `req.traceIds`, PubSub attribute propagation) always runs.

---

### Two Flows

#### CDP-initiated flow
```
CDP platform → External Connector (/in/)
             → PubSub
             → Internal Connector (/internal/)
             → AIR
```

#### AIR-initiated flow
```
AIR → Internal Connector (/out/)
    → PubSub
    → External Connector (/internal/)
    → CDP platform
```

---

### Three Route-Specific Factories

Each factory is mounted on a specific route prefix in `connector.ts`.

#### `createExternalInboundNrMiddleware()` — `/in/<platform>`

Used when an external CDP platform sends an event to the External Connector.

| Identifier | Source |
|------------|--------|
| `origin-unique-id` | Incoming `origin-unique-id` request header (omitted if absent) |
| `caller-unique-id` | Same as `origin-unique-id` at the first hop (omitted if absent) |
| `called-unique-id` | Freshly generated UUID |

#### `createOutboundNrMiddleware()` — `/out/<platform>`

Used when AIR sends an event to the Internal Connector.

| Identifier | Source |
|------------|--------|
| `origin-unique-id` | `req.body.headers.eesEventId` (the AIR event ID) |
| `caller-unique-id` | Same as `origin-unique-id` at the first hop |
| `called-unique-id` | Freshly generated UUID |

#### `createPubSubNrMiddleware()` — Internal/PubSub routes

Used when a connector receives a PubSub message from the other connector.

| Identifier | Source |
|------------|--------|
| `origin-unique-id` | `message.attributes['origin-unique-id']` (omitted if absent) |
| `caller-unique-id` | `message.attributes['called-unique-id']` (the previous hop's ID) |
| `called-unique-id` | Freshly generated UUID |

---

### PubSub Attribute Propagation

When publishing to PubSub (in `handlers.ts`), `origin-unique-id` and `called-unique-id` from `req.traceIds` are included as message attributes. This allows the second hop to reconstruct the trace chain.

### Outbound Header to AIR

When the Internal Connector calls AIR (in `EeAirClient.makeApiRequest`), the current hop's `called-unique-id` is sent as the `X-EES-CALLER-UNIQUE-ID` request header. AIR uses this to identify the connector that initiated the call.

---

### Configuration

- **`ENABLE_NEW_RELIC`** — When set to `'true'`, calls `newrelic.addCustomAttribute()` for each present trace ID. All other behaviour is unconditional.

### Benefits

- **End-to-End Traceability:** Each hop can be correlated across logs, New Relic dashboards, and PubSub messages using `origin-unique-id`.
- **Hop-level Attribution:** `caller-unique-id` identifies which service triggered the current hop.
- **Consistent Propagation:** IDs flow through HTTP headers, PubSub attributes, and log context without requiring manual wiring in each handler.
